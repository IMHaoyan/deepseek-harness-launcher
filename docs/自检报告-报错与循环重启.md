## 2. 循环重启：完整实证时间线

### 2.1 一次真实的六连崩（本机 2026-09-10，本地时间）

**六个 cycle，每个都是「就绪后 10–20 秒 code 1」。** 用户视角：页面刚出来就断，六次，然后彻底不动了。

### 2.2 为什么「回退配置」在这里是空转（机制 C）

`restoredAt:""` 是决定性证据。链路：

- `health.captureHealthy()` 只把 `configPath`（`~/.dsh/dshl/config.json`）写进快照 —— `health.js:203-232`，第 218 行 `writeDurable(path.join(staging,'config.json'), configBytes)`。
- 快照里**没有** `~/.dsh/settings.yaml`、`profiles/web/package.json`、`cordis.patch.yml`、`node_modules`。
- 崩溃根因是插件树/settings 时，`config.json` 从头没变 → `health.pickRestoreTarget()` 找不到「不同的快照」→ `health.restore()` 走 no-op → `main.js:1668` `log('config recovery: restore no-op'); return`。
- 但 `recoveryDone = true` 已在 `main.js:1664` 置位 → 下一次 `maybeAutoRestart` 直接进 `haltAutoRestart()`（`main.js:1536-1539`），且**不会**发「已自动回退」通知。

`shouldRecover` 本身也是纯计数：`attempts >= 5 && hasDifferentSnapshot`，错误文本明确不参与决策（`health.js:8`）。

**净效果：对用户最常遇到的那类崩溃，自动恢复 100% 无效，却消耗掉唯一一次恢复额度，然后把服务停在「已停止」。**

### 2.3 为什么「起不来」完全没有自动处理（机制 D）

`maybeAutoRestart()` 全仓两个调用点：`1354`（`handleUnexpectedExit` 末尾，只对「**就绪之后**退出」生效）、`1488`（补偿定时器）。

启动阶段（`child.__starting === true`）子进程退出时：

```js
// main.js:1054-1057
const expected = !!server.stopping || !!child.__starting
lifecycle.emit('service.exit', { code, signal, expected })
if (child.__starting) { server.launchUrl = null; return }   // 不标故障、不通知、不计数、不重试
```

等待循环随后 `return false`（`main.js:1082-1085`），`handleStart` 只发一条通知（`main.js:2829`）。这条路径：

- 不调 `markHealthFault()` → 不污染健康门
- 不调 `handleUnexpectedExit()` → **不计 `fastCrashStreak`**，不发 `verdict:'crash'` 交接事件
- 不触发 `maybeAutoRestart()` → **0 次自动重试**

实测：
- `lifecycle.jsonl` 全量 211 次 `service.start`，其中 **44 次在 30 秒内退出**；12 次 `expected:true`（启动阶段退出，被这条路径吃掉）。
- 09-16 05:15:55.953Z `service.start` → 05:15:56.176Z `service.exit code 1 expected:true`（**223 ms**），**没有任何 `service.autoRestart` 事件**；7 秒后那次重试来自另一个 UI 流程，不是看护。

**注意与机制 C 的分工**：5 次重试 + 硬止损那条路确实有效（09-08 15:49→15:55 完整走了一遍 attempt 1..5 → exhausted → recovery → halt；lifecycle 全量 32 autoRestart / 3 exhausted / 6 halted / 1 recovery）。它只覆盖「**端口应答过之后才崩**」这一类。

### 2.4 插件操作的并发（机制 B）—— 「装完插件 DSH 就起不来」的直接来源

代码里的不变量被写下来了，但只有一条路径遵守：

```js
// main.js:2340  「顺序执行，避免并发改同一份 profile 依赖树」
// main.js:4556-4561  只有 pluginsInstallAll 有这个守卫：
catch (e) { if (pluginInstallAllRunning) return ... }
                // main.js:4562  case 'pluginAction'—— 没有锁
```

放大并发的三个缺口：

| 缺口 | 坐标 |
| --- | --- |
| 单卡动作无全局锁 | `main.js:4562` `case 'pluginAction'` |
| `market.js` 的 busy 只按**单包**记 | `market.js:416`、`453` |
| 前台只禁用被点的那张卡的按钮 | `wwwroot/app.js:1679-1681` |
| `stopServiceForPluginChange` **忽略 `stopServer()` 的返回值** | `main.js:1934-1942`；`stopServer` 在停止进行中直接 `return false`（`main.js:1362-1366`） |
| `startServer` **没有启动中互斥**（`if (server.owned() \|\| server.claimed()) return true` 在尚无 child 时两条流程都能通过） | `main.js:911` |

实测交错（`dshl.log`，本地时间）：

### 2.5 端口：默认值踩在动态端口区间上（机制 E）

```
> netsh int ipv4 show dynamicport tcp
Start Port : 1024     Number of Ports : 13977        ← 1024–15000
```

`main.js:64` 默认端口 **3080**，正在区间内。区间内的端口会被**出站连接的临时端口**随机占用，被占用时 `listen` 报 `EACCES`（Windows 保留段）或 `EADDRINUSE`。`server.err.log` 实测致命 dump：**10× EACCES**（6 次 3080 / 4 次 3081）、**5× EADDRINUSE（全部在 4399）**。

`lifecycle.jsonl` 端口分布（全量）：**3080 × 61、3081 × 271、4399 × 85、4411 × 4**。4399 是当时启动器托管的端口，那 5 次 EADDRINUSE 就是**启动器自己的孩子在崩溃循环里抢端口**（重试前只有 `main.js:1550` 的 `await sleep(3000) // 等端口彻底释放` 这种盲等）。

代码里**已经知道这件事**（`main.js:890` 注释：「部分 Windows 机器的动态端口范围被改成 1024–15000…监听同一个端口就会随机失败」），但：

1. 默认端口没改，新装用户全部暴露；
2. `startServer` 启动前只做 `portOpen()`（**connect 探测**，400ms 超时），而 `main.js:657-658` 的注释自己写明「此时 listen 会报 EACCES，而 connect 探测却显示"空闲"——只有实际 bind 才看得出来」；
3. `canBindPort()`（真 `srv.listen`，`main.js:657-673`）写好了，**唯一调用链是 `findBindablePort:681 ← reportBindBlocked:898`——失败之后才用**。

**一个免费可得的前置判据被放在了事后。** 而且失败之后也不自愈，只留一句建议 + 一个手动按钮；又因为机制 D，这条失败**连自动重试都没有**。

### 2.6 停止 → 启动之间是盲等，没有释放确认

- owned 分支（`main.js:1376-1390`）：`killPid(pid,false)` → 最多等 1500ms → 超时 `killPid(pid,true)` → 直接 `server.child = null`。**没有确认进程已死、也没有确认端口已释放。**
- claimed 分支（`main.js:1391-1401`）：`await sleep(1000); if (await portOpen()) await killPid(pid,true)` —— 纯猜。
- 自动重启（`main.js:1550`）：`await sleep(3000)` —— 纯猜。
- 随后 `startServer` 仍只用 connect 探测（`main.js:915`）。

## 3. 「各种报错」的来源分类

### 3.1 用户看不到根因（机制 A）—— 最该先修的一条

```js
// main.js:3887-3891
// 日志与反馈页唯一日志区：给足最近 60 行（文件本身只在打开日志文件夹时看全套）
const lines = fs.readFileSync(TRAY_LOG, 'utf8').split(/\r?\n/)
logTail = lines.slice(-60).join('\n')
```

`TRAY_LOG` 是**启动器自己的**日志。DSH 侧的真因写在 `server.err.log`，全仓只出现在 `main.js:1774` 与 `4174`（诊断报告导出）。

最典型的场景于是变成：通知「服务启动失败，请打开 DSHL 控制台查看日志」→ 用户打开日志页 → 看到

```
starting DSH web (hidden window)
DSH exited unexpectedly (code 1)
```

**没有一行解释。** 真因长这样（同一台机器 `server.err.log`，按出现次数排序）：

```

       The requested module '@deepseek-ai/dsh-session' does not provide an export named 'SessionLogOffset'
```

**启动器侧对这些错误文本的处理量为 0。** 全仓只解析一种 stderr 模式：

`plugin tree failed to load` / `cannot resolve profile bundle` / `BAD_INDENT` / `does not provide an export named` —— **全部 0 命中**，没有分类、没有修复、没有转述给用户。

### 3.2 属于上游生态、但 DSHL 必须兜住的

这些不是 DSHL 的 bug，但**它们就是用户遇到的「循环重启」**：

- **插件与 DSH 版本不兼容**：`SessionLogOffset`。上游已立讨论：[Plugin-tree boot crash-loops when a plugin imports an export the bundled @deepseek-ai package no longer provides](https://github.com/deepseek-ai/deepseek-harness/discussions/5864)。
- **bundle 声明与 `node_modules` 不一致**：上游 [plugin --profile install cannot repair a bundle entry missing from "dependencies" — the suggested fix loops forever](https://github.com/deepseek-ai/deepseek-harness/discussions/4046) —— 官方给的那条修复命令本身就会死循环。
- **装完插件整个 profile 起不来**：[dsh-market#387](https://github.com/dsh-market/dsh-market/issues/387)。
- **Git 装插件未 build（无 dist/）导致 plugin tree 崩溃**：[discussion #3154](https://github.com/deepseek-ai/deepseek-harness/discussions/3154)。
- **安装报成功但静默禁用了一个无法解析的 bundle**：[discussion #1377](https://github.com/deepseek-ai/deepseek-harness/discussions/1377)。

共同特征：**同一份 profile 状态下，重试 N 次结果完全相同** —— 确定性失败，不是抖动。DSHL 没有这个判据（§2.3）。

### 3.3 profile 一致性的现状

- **DSHL 从不写 `dsh.profile.bundles`**。grep 结果是只读：`market.js:72-85`、`plugin-switch.js:186-192`、`bridge.js:250-261`。唯一写入者是 DSH CLI（`dsh plugin add/remove`）。
- 安装/卸载后的校验**只覆盖刚操作的那一个包**：`market.js:431-434`（装）、`463-466`（卸，`if (after.installed || after.bundle) throw`），`bridge.js:727-728` 同型。
- **没有 bundles ↔ `node_modules` 的全局对账**。实测漂移：`profiles/web/package.json` 声明 12 个 bundle 且**不含** `dsh-sidebar-qa`，而 `node_modules/dsh-sidebar-qa` **仍然存在**（双向漂移）。
- `cordis.patch.yml` 这一侧是**做对了**：卸载时 `pluginSwitch.removeRows()`（`main.js:2529` → `plugin-switch.js:428-436`）会摘掉 toggle/force 行并清 market disabled；`dshmarket` 卸载（`main.js:2058`）与版本升级后的旧行清理（`2515-2518`）也走了同一条路。

### 3.5 启动器自身的「上次异常退出」提示（已定位主因：**系统关机的误报**）

`lifecycle.jsonl`（09-05 → 09-16）全量：`app.started` **110** / `app.exit` **71** / `crash.previousRun` **59**；`crashStreak: 41`（`diagnostics/diag-2026-09-16-05-12-40.md`）。

| 5–30 分钟 | 40 |
| 30 分–4 小时 | 16 |
| **> 4 小时** | **13** |

**已排除的误报候选：**

| 候选 | 实测计数（`dshl.log` + `.1` + `.2`，覆盖 08-14 → 09-16） | 结论 |
| --- | --- | --- |
| 开发者热重启（`tools/dev.mjs` 强杀） | `run-guard: dev restart detected` = **0**；`…PID mismatch` = **0** | **已排除**。`dev.mjs:88-103` 先写 `.dev-restart.json` 再杀，`main.js:5329-5344` 消费它 —— 这条补偿是**对的**，且从未缺席 |

**已确证的主因 —— 系统关机/重启不走 `before-quit`：**

代码全仓 **零命中**：`session-end` / `query-session-end` / `SIGINT` / `will-quit` / `powerMonitor`。Electron 在 Windows 上关机和注销时会发 `app.on('session-end')`（Windows 专属），**没有注册**；控制台 `Ctrl+C` 在 Windows 上是 `SIGINT`，也**没有注册**（只注册了 `SIGTERM`，而 `SIGTERM` 在 Windows 上无法被 `taskkill /F` 投递）。

交叉验证（Windows 系统日志）：

```
2026/9/15 0:28:47  Id 1074  重启: 其他(计划外)
2026/9/15 0:30:51  Id 1074  重启: 操作系统: 升级(计划内)
```

对应 `lifecycle.jsonl`：上一轮 `app.started` = `2026-09-13T11:09:05.304Z`（本地 09-13 19:09），下一次 `app.started` = `2026-09-15T02:07:29.195Z`（本地 09-15 10:07）并报 `crash.previousRun{pid:113644}`。**本次重启（本地 09-15 00:28）落在这段窗口内** → 该实例是被系统重启杀掉的，不是崩溃。

> 13 次 >4 小时的运行里，多段都横跨夜间 —— 与「每次关机/重启都会在下次启动报一次『上次异常退出』+ 生成一份诊断报告」完全吻合。
> **对用户的影响**：每次关机重启后开 DSHL，都会看到「上次启动器异常退出」卡片 + 一次系统通知（`crashStreak` 累加，≥3 次进红卡档）。这是**跨用户、必然发生**的误报。

**剩余候选（40 次 <5 分钟 + 40 次 5–30 分钟，尚未收敛）：**

- `npm start` / VS Code F5 被 Ctrl+C 或停止按钮终止（无 `SIGINT` handler）→ 无 `before-quit`
- 用户手动运行 `oneClick` NSIS 安装包而启动器正在运行：安装器会终止在跑的实例
- Task Manager / 其它工具强杀

**验证方法（先量后改）**：补 `process.on('SIGINT')`、`app.on('session-end')`、`app.on('will-quit')` 的**登记日志**（不改变任何行为，只留痕），跑一周后看 59 落到哪里。**在拿到证据前不要动 `markClean` 的判定** —— 按项目原则「崩溃判定宁可少报也不误报」，先量再改。

**顺手要修的注释**：`main.js:5527-5528` 写着「开发者热重启（tools/dev.mjs 用 taskkill /F 结束进程）…收到 SIGTERM 后先清理」—— 这个注释是**过时的**：Windows 上 `taskkill /F` 是 `TerminateProcess`，该 handler 在那条路径上永远不触发；真正起作用的是 `.dev-restart.json` 标记。**注释与实现不符，改注释即可。**

### 3.6 时间口径不一致（机制 I）

- `lifecycle.js:73` → `new Date().toISOString()`（**UTC**）
- `main.js:319` → `new Date().toLocaleString('sv-SE', …)`（**本地**）
- 诊断报告文件名用 UTC（`diag-2026-09-16-05-12-40.md`），正文写本地（`生成时间：2026-09-16 13:12:40`）

这直接违反项目自己的原则「时间统一按本地时间展示」。本次排查中我因此先按错误的小时区间 grep，得出过「日志里没有生命周期记录」的错误结论。

## 4. 修复建议（按性价比排序）

> 状态：**P0 与 P1 已全部落地**（见 §1.5），P2 / P3 待排期。

### P0 —— 让用户第一次就看到原因 / 不再被必然误报打扰 ✅ 已落地

1. **控制台日志区可切 `server.err.log`**（或崩溃时把最后 N 行 stderr 内联进状态推送）。
   代价：一个 tab / 一个字段，约 30 行。收益：§3.1 全部场景立刻可自助定位。
2. **崩溃通知正文带一行真因**：`handleUnexpectedExit` / 启动失败时从 `server.err.log` 尾部提取首个 `Error:` 行（复用 `redact()`），塞进系统通知与控制台卡片。
   代价：一个纯函数 + 单测。风险：需确保 `redact()` 覆盖（已有 launch token 脱敏测试）。
3. **消除「关机/注销 = 异常退出」的必然误报**（§3.5，跨用户必然发生）：
   注册 `app.on('session-end')`（Windows 关机/注销）与 `process.on('SIGINT')`，命中时走 `markClean()`；`app.on('will-quit')` 作为兜底。
   代价：极小（三个 handler）。**收益：每次重启电脑后少一张崩溃卡 + 一次通知 + 一份诊断报告。**
   **注意**：必须保留 `.dev-restart.json` 那条既有路径不动 —— 它是对的，别一起「重构」掉。

### P1 —— 让自动恢复对这个故障面真的有用 ✅ 已落地

4. **插件操作全局互斥**（机制 B，§2.4）：`pluginAction` 与 `pluginsInstallAll` 共用一把锁；`stopServiceForPluginChange` 必须尊重 `stopServer()` 的返回值；`startServer` 加启动中标志。
   代价：小～中。收益：直接消掉「装完插件就起不来」这一类。
   **不变量已有文字描述（`main.js:2340`），补的是执行。**
5. **确定性失败判据**：连续 N 次启动失败的**首个错误行归一化后相同** → 判 `deterministic`，跳过剩余重试，直接进入修复引导（而不是把 5 次额度烧完再空转一次回退）。
   代价：纯函数 `classifyBootFailure(errTail)` + 状态位。
6. **扩展健康快照覆盖面**（或新增独立的「profile 检查点」）：把 `settings.yaml` + `profiles/web/package.json` + `cordis.patch.yml` 纳入快照与回退。
   代价：中（需按既有 fail-closed 风格做原子写入 + sha256 + 槽位轮转）。收益：让「已自动回退」第一次变成真的。
7. **插件树自愈**：错误文本命中 `cannot resolve profile bundle "X"` / `does not provide an export named` / `plugin tree failed to load` 时，按 `plugin-switch` 已有能力禁用对应 loader entry，再重试一次；修不动就点名是哪个插件 + 给「禁用该插件后启动」一键入口。
   代价：中。必须 fail-closed（改前备份 `package.json` / `cordis.patch.yml`，与现有备份风格一致）。

### P2 —— 端口与启动阶段（待排期）

8. **启动前 bind 预检**：spawn 之前 `await canBindPort(PORT)`；不可 bind 时**自动**切到最近的 bindable 端口（记 `service.portSwitch` + 一条用户可见提示）。
   代价：小（`canBindPort` 已存在）。**需决策**：是否允许自动换端口（影响书签/固定链接）。
   **建议：首次启动自动切 + 明确告知；用户显式配置过端口时不自动切，只提示。**
9. **默认端口移出动态区间**：`3080` → `15081+`。代价极小。**风险**：老用户配置里已存 3080，只改默认值、不动已存配置。
10. **启动阶段失败纳入看护**（机制 D）：`child.__starting` 期间退出也计 `fastCrashStreak` + 触发一次有界重试；`reportBindBlocked` 后自动重试一次换端口。
    代价：小。**风险**：必须排除 `update.dsh` 装卸插件的受控退出（那些是 `expected:true`，语义不同）。
11. **停止/重启改成等释放而不是盲等**：`stopServer` 后轮询 `canBindPort(PORT)` 通过再 spawn，替换 `sleep(3000)`。

### P3 —— 语义与噪音（待排期）

12. **统一时间口径**：`lifecycle.js` 改用本地时间（与 `dshl.log` 一致），诊断报告文件名同步。
13. **修掉与实现不符的注释**：`main.js:5527-5528` 说靠 `SIGTERM` 兜开发者热重启 —— 实际靠 `.dev-restart.json`。改注释，不改代码。
14. **插件批量操作合并重启**：连续单动作也走 `deferPluginChange`，把「装 3 个插件 = 3 次重启」压成 1 次。
